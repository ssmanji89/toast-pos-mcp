# Threat Model: Local Distribution, AI-Provider Data Flow, and Future Remote Transport

**Status:** current, reviewable  
**Last reviewed:** 2026-07-29  
**Scope:** the architecture decided in [`public-use-boundary.md`](public-use-boundary.md), evaluated against the code merged to `main` through T1-004, with T1-005 recorded as claimed but not yet merged and T1-006 onward not yet started  
**Method:** asset/boundary enumeration plus per-area threat walkthrough, grounded in the source files and tests present at review time rather than in the planned end-state design

This document extends the accepted architecture decision with a concrete threat catalog. It does not reopen or restate the decision itself; where the two overlap, `public-use-boundary.md` remains the authority on what the product *will* do, and this document is the authority on what can go wrong and what already mitigates it *today*.

## 0. Ground truth at time of writing

Before modeling threats, this section fixes what actually exists, because a threat model for planned features would be fiction.

Per `LOOP.md`, slices T0-001 through T1-004 are `CLOSED` and merged. T1-005 (configuration page-token pagination) is `CLAIMED` — claimed by a builder but not built, reviewed, or merged. T1-006 onward (`/ordersBulk` pagination, location/capability discovery, all normalization and reporting tools, cash and labor reporting, the Analytics adapter) are `OPEN` — not started.

Concretely, `src/` contains exactly five files: `config.ts`, `auth.ts`, `transport.ts`, `server.ts`, and `index.ts`. There is:

- **no pagination code of any kind** — no `/ordersBulk` traversal, no `Toast-Next-Page-Token` handling;
- **no location or capability discovery**;
- **no normalization, report calculation, or Analytics adapter code**;
- **zero registered MCP tools, resources, or prompts** (`server.ts` constructs a bare `McpServer` with no `registerTool`/`server.tool`/equivalent call anywhere in the tree — confirmed by direct search);
- **no code path that has ever requested, received, or held a single byte of real or synthetic Toast Merchant Data** — the only network calls that exist are the OAuth token exchange (`src/auth.ts`) and a generic, currently-uninvoked `GET` capability on the shared HTTP client (`src/transport.ts`).

This matters for every section below: several threats that will be sharp once reporting tools exist (guest-data exposure, report-content exfiltration to an AI provider, cross-location data bleed in report output) have **no live instance today** because there is no Merchant-Data-bearing code path for them to act on yet. Where a control is described as "implemented," it is implemented in the credential/transport/startup layer that exists now, not in reporting tools that do not exist yet. This document says so explicitly rather than describing planned tools as if they were already built.

## 1. Assets and trust boundaries

| Asset | Where it lives today | Sensitivity | Boundaries it crosses |
|---|---|---|---|
| Toast OAuth client ID / client secret | `src/config.ts`, module-private `WeakMap` | Long-lived credential; compromise grants everything the credential is scoped for | Operator's `.env`/secret store → process memory → (as a request body) → Toast's authentication endpoint over TLS |
| Toast OAuth bearer access token | `src/auth.ts`, native `#` private class field | Short-lived (≤24h, capped) credential; compromise grants API access for its remaining lifetime | Toast's authentication endpoint → process memory → (as an `authorization` header) → Toast Data API over TLS |
| Toast Merchant Data (orders, payments, labor, cash, menu, aggregated reports) | **Not present in the codebase yet** — no tool retrieves it | Restaurant financial/operational data; regulated by Toast's API Terms regardless of sensitivity label | Future: Toast Data API → this process → MCP host → (if the host forwards tool output to a model) cloud model provider and its subprocessors |
| Restaurant GUID / management-group identifiers | Passed through `transport.ts` request options and rate-limit keys today; used nowhere else yet | Low sensitivity alone, but load-bearing for isolation (rule 6) | Operator config or future discovery response → in-memory cache/rate-limit keys |
| Runtime environment variables (`TOAST_API_HOSTNAME`, `TOAST_CLIENT_ID`, `TOAST_CLIENT_SECRET`, `TOAST_ACCESS_TYPE`, `TOAST_DEFAULT_RESTAURANT_GUID`, `TOAST_MERCHANT_AI_CONSENT_ACKNOWLEDGED`) | Operator's shell/process environment; read once by `loadRuntimeConfig()` | Contains the two credential values above, plus the consent gate | Operator's shell/secret manager → process environment → `src/config.ts` |
| The npm dependency tree | `package-lock.json` | Build-time and run-time code-execution trust | npm registry → local `node_modules` → this process |
| The MCP host process | External to this repository | Fully co-equal trust with the operator for whatever it is configured to pass in | Operator's machine → spawns this process → stdio pipe both ways |
| Report outputs | **Not present yet** | Will carry Merchant Data once T3+ ships | Future: this process → stdio → MCP host → wherever the host sends tool results next |

### Trust boundary diagram (textual)

```
Operator secret store / shell env
        |  (env vars, in-process only; never persisted by this repo)
        v
toast-pos-mcp process  <-- stdio JSON-RPC -->  MCP host process (Claude Desktop, Claude Code, another agent runtime, ...)
        |  (HTTPS, bearer token / client-credentials body)                 |
        v                                                                  v  (host's own egress; outside this repo's control)
   Toast Cloud (auth + Data API)                                   Cloud model provider + its logging/telemetry/subprocessors
```

The most consequential trust boundary in the whole system is the second arrow: **the MCP host is trusted with everything this server is trusted with.** In the common case, the host is the process that spawns `toast-pos-mcp` and supplies its environment variables (for example, an `env` block in a Claude Desktop or Claude Code MCP server configuration). A host configured that way already possesses `TOAST_CLIENT_ID`/`TOAST_CLIENT_SECRET` before this server ever runs — it is not a hypothetical "what if the host is malicious," it is a standing structural fact that the credential-issuing party (the operator, via their MCP client configuration) and the credential-consuming party (this server) are both fully subordinate to whatever spawned the process. This repository has no way to reduce that boundary from local `stdio`; only a differently-shaped distribution (out of scope, see §3) could put a narrower-scoped credential in front of the host instead of the whole client-secret pair.

## 2. Local stdio distribution

### 2.1 Credential custody on the operator machine

- **Environment-variable exposure.** `TOAST_CLIENT_ID`/`TOAST_CLIENT_SECRET` live in the process environment for the life of the process. On POSIX systems any process with permission to read `/proc/<pid>/environ` (same user, or root) can read them; on any OS, a debugger attached to the process, or a crash/core dump, can recover them from memory regardless of the in-process protections described in §6. This repository cannot fix OS-level process isolation; the mitigation available to it — never persisting the values, never echoing them into logs or errors (§6) — is applied.
- **Shell history.** If an operator exports these variables inline (`TOAST_CLIENT_SECRET=... node dist/index.js`) rather than sourcing them from a secrets manager or an untracked `.env` file, common shells record the literal command, secret included, in the history file. The README's example invocation (lines demonstrating `TOAST_CLIENT_SECRET=your-client-secret ... node dist/index.js`) is itself a shell-history-exposure pattern if copied verbatim with a real secret; this is a documentation-hygiene gap worth flagging for T6-002 rather than a defect in the running code.
- **Process listings.** Standard `ps`/Task Manager output does not show environment variables by default on most platforms, so this is a narrower exposure than `/proc/<pid>/environ`, but it is not zero on systems or configurations where full command lines (including any inline-exported secret, per the shell-history case above) are visible to other local users.
- **Core dumps and memory inspection.** Both the `WeakMap`-held client secret (`src/config.ts`) and the private-field-held bearer token (`src/auth.ts`) are ordinary JavaScript heap values at the V8 level. Every protection described in §6 defends against *language-level reflection* (enumeration, serialization, spreading, cloning, `util.inspect`) — none of it defends against a process memory dump, a debugger with `--inspect` attached, or a swap file containing the process's heap. This is a real, unmitigated residual risk (see §7), not a gap in the described controls; it is out of scope for a Node.js application to close entirely.
- **Other local processes / same-machine attackers.** A co-resident process running as the same OS user is already inside the trust boundary this architecture assumes (per-operator local execution). A different-user or elevated attacker on the same machine is a host-OS security problem this repository cannot solve; it is explicitly why `public-use-boundary.md` treats a hosted, multi-tenant, always-on credential store as a categorically different (and currently forbidden) risk profile — see §3.
- **A malicious or compromised MCP host.** Covered above as a trust-boundary fact rather than a residual gap: the host that spawns this process, in the common configuration, already holds the credential it passes in. A host that is compromised *after* spawning the child inherits whatever this process does over the stdio pipe. Today that surface is minimal — `server.ts` registers no tools, so a compromised host talking to this server can, at most, exercise the base MCP handshake (`initialize`, an empty tool/resource/prompt listing). That surface will grow once T3+ ships Merchant-Data-bearing tools, and reviewing this section again at that point is appropriate.

### 2.2 The npm supply chain

The dependency surface is deliberately small: two direct dependencies (`@modelcontextprotocol/sdk@1.29.0`, `zod@4.4.3`), resolving to 96 packages total in `package-lock.json`, verified by a clean `npm ci` (96 packages added, exit 0; see §8). `npm ci` installs strictly from the committed lockfile and verifies each package's recorded integrity hash, which defends against a tampered or substituted registry response for anything already recorded in the lockfile. It does **not** defend against a contributor or agent being persuaded to fetch package bytes from somewhere other than the registry/lockfile path in the first place — which is exactly what the realized incident below did.

**Realized threat, with the mitigation applied — `T1-001-R2-S1`.** During review of an earlier pull request in this repository, two instructions appeared that pointed at npm and pnpm package bytes hosted in unrelated third parties' GitHub repositories, framed as a cache-archive workaround for a failing registry mirror — a plausible-sounding pretext for fetching binary content from outside the recorded, hash-verified lockfile path. This is not a hypothetical supply-chain scenario; it happened in this repository's history. The mitigation actually applied: the `tmp/pnpm-transfer` branch carrying the instructions was deleted, the provenance-probe comment on the originating pull request was replaced with a repudiation, and the original artifacts were archived offline for record-keeping. No package bytes from either third-party source were ever fetched or installed — the incident was caught and reversed before any bytes crossed the boundary, not after. The residual lesson: a "failing registry mirror, use this alternate source instead" pretext is a realistic vector for this project specifically, because Toast's production-only Standard API access model already trains contributors to expect friction and workarounds around external infrastructure; that same expectation is exploitable. No automated control currently exists to catch a recurrence other than reviewer vigilance — see §7.

### 2.3 Shell history, environment, and secrets hygiene — summary

None of the above have or need in-repository code fixes; they are operator-facing operational risks. The repository's obligation, met by `AGENTS.md` rule 2 and its implementation in `src/config.ts`, is to never widen the exposure itself (no logging, no serialization, no disk persistence of the credential values it receives).

## 3. AI-provider data flow

This is the sharpest area because local execution is routinely (and incorrectly) read as "safe by default." It is not: `public-use-boundary.md` states plainly that "[l]ocal execution controls credential custody; it does not authorize AI or third-party processing," and the code enforces a hard gate on that distinction.

### 3.1 The consent gate, precisely

`src/config.ts` requires `TOAST_MERCHANT_AI_CONSENT_ACKNOWLEDGED` to equal the **exact string** `"true"` (`REQUIRED_CONSENT_ACKNOWLEDGMENT`, `consentSchema = z.literal("true")`). Every other value — unset, empty, `"1"`, `"yes"`, `"True"`, `"TRUE"` — is rejected and added to the aggregated validation-issue list; `loadRuntimeConfig()` throws `RuntimeConfigError` if any issue exists, including this one, and the message never echoes the offending value. `src/index.ts` calls `loadRuntimeConfig()` synchronously before constructing the token manager, the HTTP client, or the MCP server, and before `server.connect(transport)` — so the entire process fails closed before the MCP transport ever opens if consent has not been acknowledged. This is verified directly by two tests in `test/server.test.ts` ("fails closed and exits non-zero when Merchant-AI-consent acknowledgment is absent, without leaking the configured secret"; "fails closed and exits non-zero when required runtime configuration is entirely missing") and by dedicated unit coverage in `test/config.test.ts` ("fails closed when consent acknowledgment is absent," "...is explicitly false," "accepts only the exact string \"true\"").

Two things this gate is honest about, and that this document repeats because they are easy to lose in a security review: the acknowledgment **records operator intent only**. `src/config.ts`'s own doc comment and `public-use-boundary.md` both say this explicitly — it "cannot and does not establish legal sufficiency of Merchant consent." Setting the variable to `"true"` is a claim the operator is making about a fact outside this repository (that they hold documented Merchant consent and have satisfied any Toast prior-written-consent requirement); the code has no way to verify the claim and does not attempt to.

### 3.2 What the gate actually gates today — an honest gap

Because zero MCP tools are registered (§0), the consent gate currently has nothing to gate except *the server's own willingness to start at all*. There is no Merchant-Data-bearing tool call today for the acknowledgment to be checked against a second time. This surfaces a forward-looking design question this document flags rather than fixes (per the builder constraint — this is not a defect, since nothing today violates the consent requirement; there is simply nothing yet for it to apply to): `server.ts`'s `createServer()` accepts only a `toastHttpClient` option, not the `RuntimeConfig` itself, so the validated consent acknowledgment is not currently threaded into the layer where future tools will be registered. When T3 (or any AI-facing tool surface) is built, whoever implements it must deliberately re-derive or re-thread the consent flag (or the whole `RuntimeConfig`) into tool registration; nothing in the current plumbing does this automatically, and nothing in the current architecture prevents a future implementer from registering a Merchant-Data tool without re-checking it, because the check today is a startup gate, not a per-call gate. This is recorded here as a residual item for the T3 planner/reviewer to hold as an explicit acceptance criterion, not as something T6-001 should implement.

### 3.3 The full data-flow path once tools exist

Toast Cloud → (HTTPS, this process's own egress) → this process's memory → (stdio JSON-RPC tool result) → MCP host process → (the host's own egress, entirely outside this repository) → whichever cloud model provider, prompt/tool-logging pipeline, tracing/telemetry collector, and subprocessor chain the host and operator have configured. Only the first hop is this repository's to control. The second and third are the actual "AI-provider data flow" the slice name refers to, and this repository cannot inspect, log, or enforce anything about them — it can only require the operator's acknowledgment before it will emit anything at all. Concretely, no technical control anywhere in this codebase or its dependencies can:

- prevent the MCP host from persisting tool-call arguments/results in its own logs, independent of anything this server does;
- prevent a cloud model provider from retaining prompt/tool content according to its own retention policy;
- verify that a provider's "no training on this data" setting is actually honored, or that it covers logging, human review, residency, or subprocessors (the exact point `public-use-boundary.md` makes: "[a] provider's 'no training' setting does not resolve logging, retention, human-review, residency, or subprocessor obligations").

### 3.4 Training/model-improvement prohibition

`AGENTS.md` rule 4 and the Toast API Terms summarized in the research doc prohibit using the API or data passing through it to train, fine-tune, evaluate for model improvement, or generate API-derived synthetic training data without Toast's prior written approval. This repository has no code-level enforcement point for this today (there is no Merchant Data flowing yet), and cannot have one after the fact either — it is a downstream configuration and contractual obligation on the operator's chosen model provider, not something interceptable in this process. The repository's obligation is the one it already meets: never itself deriving fixtures, examples, or training data from real Toast API responses (`AGENTS.md` rule 3; `test/support/synthetic-fixtures.ts` and `test/fixtures/synthetic/` are independently invented, not derived).

## 4. Future remote transport (out of scope, modeled only)

`AGENTS.md`'s architecture constraints state remote Streamable HTTP "requires a separate threat model, authentication design, Toast approval review, and tenant-isolation review." Nothing in this slice builds it. This section exists only to describe what such a review would need to cover, so that a future decision starts from an accurate list rather than from scratch.

- **Authentication design.** Today, "authentication" is a 1:1 mapping: one operator, one process, one Toast client-credentials pair, live only in that process's memory for that process's lifetime. A remote, always-on service would need two separate authentication layers that don't exist today: (a) authenticating the *remote MCP client* to the hosted service itself (API keys, OAuth, mTLS — none of which this repository implements), independent from (b) the Toast credential the service holds on the tenant's behalf. Conflating these, or omitting (a) and relying solely on knowledge of a Toast credential, would let anyone who can reach the network endpoint impersonate any onboarded tenant.
- **Tenant isolation.** The one isolation axis that exists today — rate-limit state keyed by `apiFamily:restaurantGuid:key` (`src/transport.ts`, `rateLimitStateKey`) — is sufficient for a single operator with one credential across possibly multiple locations, because within one process there is exactly one credential in play. It is **not** sufficient for multi-tenant hosting: nothing in that key includes a credential or tenant identity, only a restaurant GUID. A hosted service would need every cache, rate-limit bucket, token, and pending-job entry keyed by tenant/credential identity *in addition to* restaurant GUID, specifically so that tenant A's request path can never read tenant B's cached bearer token, rate-limit state, or (once it exists) report cache — even if both tenants happen to reference the same or overlapping restaurant GUIDs. Today's structural fix for the single-tenant rate-limit bug (`T1-004-R1-S1`/`F7`, described in `LOOP.md`) is a useful precedent for the *shape* of the fix a hosted version would need, but it is not itself sufficient once a second tenant enters the picture.
- **Credential brokerage risk.** A hosted, multi-tenant service that stores many merchants' Toast client secrets at rest becomes a single high-value target: compromising the host discloses every onboarded merchant's Toast access simultaneously, a materially different blast radius than compromising one operator's local machine. This is precisely why `public-use-boundary.md` and `LOOP.md`'s product boundary forbid "a hosted multi-tenant credential-processing service" and "[s]hared project credentials or credential brokerage" in the current architecture — not as an arbitrary scope limit, but because centralizing many merchants' credentials behind one service plausibly also triggers Toast API Terms section 2.6 (prior written consent required before engaging a third-party provider to use the APIs in connection with application development) in a way that per-operator local execution does not.
- **New asset class: credentials at rest.** Local `stdio` never persists a credential to disk. A remote service necessarily would (encrypted secret store, key management, rotation, deletion-on-offboarding) — an entire asset class and control surface (encryption at rest, access logging, key rotation, incident response for a live secret store) that has no analog in the current architecture and is not modeled further here because it depends on decisions (which provider, which region, which retention policy) that don't exist yet.
- **Network-listener threats with no current analog.** TLS termination and certificate management, DoS/rate-limiting of the service's own endpoint (distinct from Toast's rate limits), origin/CSRF validation for any HTTP-adjacent transport, and incident response for a service holding live credentials continuously rather than only in one operator's process memory during a session.

None of this is built, and this document does not recommend building it; it exists so that the day someone proposes it, the review has a checklist instead of a blank page.

## 5. Data classes and exclusions

`AGENTS.md` rule 5 and `public-use-boundary.md` exclude guest PII, delivery addresses, Analytics guest-payment data, and `cardFingerprint` from the initial product. No code exists yet that could violate this (there is no reporting tool at all), so this section is necessarily about the *design commitment* recorded in the governing docs, evaluated for why it is the right shape rather than about code that enforces it today.

**Why exclusion at the request layer is stronger than filtering after retrieval.** Toast's OAuth client-credentials model scopes access at credential-configuration time in Toast Web, not per-request — this project's `auth.ts` posts `clientId`, `clientSecret`, and `userAccessType` to the login endpoint and never includes a scope-selection parameter, because Toast does not offer one at that layer (scopes are bound to how the operator configured their credential in Toast Web). The actual mechanism by which guest data is excluded is therefore two-layered: (1) the operator's Toast Web credential configuration determines what the issued token is authorized to reach at all, and (2) — the layer this codebase controls — the code never calls `guest.pi:read`-gated endpoints, never calls `delivery_info.address:read`-gated endpoints, and never calls the Analytics guest-payment dataset endpoint. Layer (2) is a request-layer exclusion: the excluded data is never fetched, so it never transits the network into this process, never exists in this process's memory, is never subject to a logging/serialization bug, and is never one missed redaction away from leaking.

Contrast that with filtering after retrieval — fetching the full order/check payload (which may include guest name, a delivery address, or a nested field the operator's scope happens to permit) and stripping the sensitive fields before returning a report. That approach has all of the request-layer approach's blast radius plus more: the excluded data exists in process memory, in transit, and potentially in any error path, debug log, or serialization surface for the lifetime of that retrieval, and its exclusion depends on a filter being complete and correct on every code path, forever, including new fields Toast adds later. `AGENTS.md` rule 2's principle — "[r]edaction is not a substitute for avoiding capture" — is written for credentials, but rule 5 applies the identical logic to guest-linked data: "[a]ggregating a result does not make source-data processing permissible." Never requesting the data closes the entire class of "we fetched it and then failed to filter it correctly" bugs by construction; it cannot be defeated by a missed field, a nested modifier, or a new Toast enum value the filter doesn't yet know about (the exact kind of forward-compatibility gap the 2026-07-20 open-enum change makes newly relevant).

This is currently a documentation-and-intent commitment, not an enforced runtime check, because there is no reporting code yet to enforce it against. The threat model's job here is to confirm the *design* is the stronger of the two available shapes, which it is, and to flag that T3/T5 implementers must actually follow it rather than reach for the easier-looking "fetch broad, filter narrow" pattern once real endpoints are being wired up.

## 6. Controls implemented today, with file-level evidence

The slice brief supplied a starting list to verify or correct. Each item below states what was actually found, with corrections where the starting claim overstated, understated, or was simply not yet true.

1. **"Credentials held in a module-private `WeakMap` reachable only through a named accessor (`src/config.ts`)."** Confirmed as described. `credentialsByConfig` (a `WeakMap<RuntimeConfig, RuntimeConfigCredentials>`, `src/config.ts:123`) holds `clientId`/`clientSecret` keyed by the frozen `RuntimeConfig` object's identity; the sole accessor is `getRuntimeConfigCredentials()` (`src/config.ts:142-154`), which throws `TypeError` for any config object it did not itself produce. `test/config.test.ts`'s "probe table: none of the eleven access patterns reach the raw client secret" exercises `Object.keys`, `Object.entries`, `Object.values`, spread, `Object.assign`, `structuredClone`, `for...in`, and `util.inspect` (including `showHidden`/`customInspect: false`) against the config object and asserts none surface the secret. **Correction/nuance:** this defends against *JavaScript-level* reflection and serialization — exactly the realistic threat from a logging library, an error serializer, or a dependency doing generic object enumeration. It does **not** and cannot defend against process memory inspection, a debugger, or a core dump; the plaintext secret is still an ordinary value on the V8 heap. The claim as given did not say otherwise, but a reader could reasonably infer stronger protection than exists, so this document states the boundary explicitly (see §2.1).
2. **"Bearer tokens in native `#` private class fields (`src/auth.ts`)."** Confirmed exactly. `#cachedToken` (`src/auth.ts:80-85`) is a true ECMAScript private field, not merely a naming convention — it has no bracket-notation access and is not visible to `Object.getOwnPropertyNames`, `Reflect.ownKeys`, or any enumeration idiom, which is a structurally stronger guarantee against JS-level reflection than the `WeakMap` pattern in `config.ts` (a `WeakMap` key is still an ordinary reference; a private field is invisible to reflection entirely). `test/auth.test.ts`'s "does not expose cached bearer tokens through manager enumeration or inspection" test exercises `Object.keys`, `Object.getOwnPropertyNames`, `Object.entries`, `Object.values`, spread, `Object.assign`, `structuredClone`, `util.inspect` (`showHidden: true`, `customInspect: false`), `JSON.stringify`, and a `for...in` loop against the token manager and asserts none surface the token or the underlying client secret. The same memory-inspection caveat from item 1 applies here too.
3. **"Errors carrying only status and a request id, with no upstream body and no `cause`."** Confirmed for both error classes present today. `ToastAuthError` (`src/auth.ts:58-77`) and `ToastHttpError` (`src/transport.ts:65-90`) each carry only `code`, `message` (a fixed, non-interpolated string per error path), `upstreamStatus`, and `upstreamRequestId` (read from the `toast-request-id` header via `buildAuthErrorMetadata`/`requestIdMetadata`, never the response body). A direct search of `src/` found zero occurrences of a `cause` property being set anywhere (the only two textual matches for "cause" in the tree are prose in doc comments, not code). Every `catch` block that could see an upstream body or a caught exception's message (the OAuth fetch failure, the Toast data fetch failure, invalid-JSON parsing in both files) deliberately discards the caught value and throws a fixed message instead — verified by inline comments explaining exactly this discipline in both files and by tests asserting sanitized handling (`test/auth.test.ts`: "wraps a rejected token fetch in a sanitized ToastAuthError without leaking the caught error's detail"; `test/transport.test.ts`: "does not retry authorization or validation failures and does not expose upstream bodies").
4. **"Structurally GET-only transport via a hardcoded method literal (`src/transport.ts`)."** Confirmed, with a scope correction. `ToastHttpClient.getJson()` has exactly one `fetch` call site in the entire class (`src/transport.ts:175-182`), with `method: "GET"` as a literal — there is no parameter, branch, or code path anywhere in `transport.ts` that can select a different HTTP verb; grepping the file for method literals finds only this one `"GET"`. This is a genuine structural (not merely conventional) enforcement of `AGENTS.md` rule 1 for the Toast **Data** API client specifically. **Correction:** the claim should not be read as "the whole system is structurally GET-only forever." `src/auth.ts` necessarily issues one hardcoded `"POST"` (`src/auth.ts:138`) — to Toast's *authentication* endpoint, not a Data API write, which is the correct separation per `AGENTS.md`'s instruction to keep authentication and data transport as distinct layers. More importantly, `docs/research/toast-api-reporting-landscape.md`'s own Analytics report-job lifecycle requires a `POST` to create a report request (§"Analytics report jobs"), which T5-002 will have to implement. When that lands, the "structurally read-only" guarantee for the *whole* system will necessarily move from "one hardcoded GET literal covers every Toast Data API call" to something like "only the two documented Analytics verbs (`POST`-create, `GET`-retrieve) are reachable, and neither is a Toast write operation" — a real but different structural guarantee that T5 must establish and a future reviewer must re-verify. This document flags that the current single-file GET-only structure is accurate for what exists today (the Standard API adapter) and is not a claim about the system's permanent shape.
5. **"Rate-limit and configuration page state bound to restaurant GUID."** Only half of this is currently true, and the other half does not exist in the codebase at all. Rate-limit state **is** bound to restaurant GUID: `rateLimitStateKey(apiFamily, restaurantGuid, key)` (`src/transport.ts:453-459`) makes `restaurantGuid` a required parameter, not an optional convention, closing the exact cross-location leak recorded as `T1-004-R1-S1`/`F7` in `LOOP.md` (reproduced live: one restaurant's exhausted quota previously blocked an unrelated restaurant for 30 seconds) — verified by `test/transport.test.ts`'s "does not cross-contaminate rate-limit state between restaurant GUIDs sharing a limiter key" test. **"Configuration page state," however, does not exist yet.** There is no page-token pagination code anywhere in `src/` — confirmed by a direct listing of the source tree, which contains only `config.ts`, `auth.ts`, `transport.ts`, `server.ts`, and `index.ts`. T1-005 ("Implement configuration page-token iteration, duplicate-token guards, and scoped 409 restart behavior") is recorded in `LOOP.md`'s ledger as `CLAIMED`, not `BUILT`/`CLEAN`/`MERGED`/`CLOSED` — claimed by a builder, but no corresponding code has landed on `main`. This half of the starting claim should be read as a correctly documented *requirement* (in `AGENTS.md` rule 6, the research doc, and the pagination section of `public-use-boundary.md`) for a slice that has not shipped, not as an implemented control today.
6. **"Fail-closed startup before the MCP transport opens (`src/index.ts`)."** Confirmed. `main()` (`src/index.ts:10-23`) calls `loadRuntimeConfig()` — which throws on any invalid or missing field, including a missing or non-`"true"` consent acknowledgment — before constructing the token manager, the HTTP client, or the server, and before `await server.connect(transport)`. The top-level `.catch()` (`src/index.ts:25-30`) deliberately prints only a generic `"toast-pos-mcp failed to start"` to stderr rather than the caught error's detail, so a credential-bearing validation message cannot leak through this final layer even if an earlier layer's sanitization were ever imperfect. Verified by `test/server.test.ts`'s two fail-closed startup tests referenced in item 3.

**Additional controls found during review, not on the starting list, worth recording for completeness:**

- The exact-string consent gate itself (`src/config.ts:33`, `316-335`) is a control in its own right, distinct from the general validation machinery — it specifically refuses truthy-looking-but-wrong values (`"1"`, `"yes"`, `"True"`) rather than coercing them, which is a meaningfully stricter fail-closed posture than a typical boolean-env-var parser.
- Token-acquisition failures are classified as non-retryable and are structurally prevented from reaching the network at all (`src/transport.ts:162-171`, `T1-004-R1-F1`): the authorization header is acquired in its own `try`/`catch` before the fetch `try` block, so an expired or invalid credential fails immediately with `token_acquisition_failed` instead of being retried to the attempt ceiling under a misleading "network failure" classification.
- A bounded rate-limit wait ceiling (`DEFAULT_MAX_RATE_LIMIT_WAIT_MS`, 15 minutes; `src/transport.ts:33`) prevents a hostile or corrupted `Retry-After`/reset header from hanging this locally-run process indefinitely — an availability control for the operator's own machine, not just a correctness fix (`T1-004-R1-F2`).
- Hostname validation (`validateHostname`, `src/config.ts:167-211`) rejects a configured `TOAST_API_HOSTNAME` containing a URL scheme, path, or query string, which prevents a misconfigured or maliciously-supplied hostname value from redirecting requests to an unexpected path or injecting query parameters into the constructed request URL.
- The current absence of any registered MCP tool (§0) is itself a meaningful, if temporary, mitigating fact: the live attack surface reachable through a compromised MCP host today is limited to the base MCP handshake, because there is no Merchant-Data-bearing tool-call surface yet. This is not a permanent architectural control — it is a fact about the current slice boundary that will change the moment T3 ships.

## 7. Residual risk

Stated directly, in order of how soon each one matters:

- **The Analytics wait-ceiling mismatch, carried forward from `LOOP.md`'s T1-004 closure.** `DEFAULT_MAX_RATE_LIMIT_WAIT_MS` (15 minutes) is scoped to the Standard API, whose longest documented rate-limit window is the global 10,000-requests-per-15-minutes bucket. `docs/research/toast-api-reporting-landscape.md` documents Analytics POST limits as low as 10 requests/hour. If T5's Analytics adapter reuses this constant unmodified, a legitimate Analytics wait that Toast's own documented behavior would expect to honor could instead fail closed with `rate_limit_wait_exceeded` well before the wait Toast actually requires. This is a correctness/availability risk for the Analytics adapter specifically, not a security defect in the code that exists today; it is recorded here because it is exactly the kind of "silently reused assumption" a threat review exists to catch before it ships.
- **The `expiresIn: 86400` accepted-boundary assertion gap, carried forward from T1-003.** `LOOP.md` records that no test asserts the *accepted* side of the 24-hour expiry ceiling — that a token response with `expiresIn: 86400` exactly succeeds rather than being rejected by the `.max(86_400)` schema boundary. This is still true at the current head: `test/auth.test.ts` contains no reference to `86400` at all. The rejected side (values above 86,400) is well covered ("rejects expiresIn values above the documented 24-hour sanity ceiling"), but the accepted boundary itself has only been "[c]onfirmed working by direct probe" per `LOOP.md`, not by a committed test. This is a test-coverage gap, not a runtime defect — `.max()` is inclusive, so 86,400 is accepted today — but it means a future refactor of the schema could silently flip that boundary without any test failing.
- **The consent gate is a startup-time check with nothing yet to gate at call time (§3.2).** Not a defect — there is no Merchant-Data tool yet — but a live design risk for whoever builds T3: the acknowledgment is not currently threaded into `server.ts`'s tool-registration surface, so nothing today would catch a future tool being registered without re-deriving the consent state.
- **Process-memory and core-dump exposure of credentials and bearer tokens (§2.1, §6 items 1-2) is entirely unmitigated and cannot be fully mitigated by this codebase.** This is a known, accepted limit of running any credential-holding process on an operator-controlled machine, not a gap specific to this project's implementation choices.
- **The npm supply-chain incident's underlying pretext (a "workaround" for infrastructure friction) has no automated detection today** beyond reviewer vigilance; the specific instance was caught and reversed (§2.2), but nothing structural prevents a similarly-framed attempt from recurring.
- **Guest-data and remote-transport risks (§3.3-3.4, §4) have no code to evaluate yet.** They are modeled here so the eventual implementation has a checklist, not because anything currently violates them.
- **Shell-history exposure from copy-pasted inline credential invocations** (§2.1) is a documentation-hygiene item appropriate for T6-002's operator documentation, not a code change.
