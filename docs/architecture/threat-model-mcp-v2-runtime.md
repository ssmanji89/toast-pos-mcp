# Threat Model Addendum: MCP v2 Local Stdio Runtime

**Status:** current for the pre-T3 MCP v2 migration branch  
**Last reviewed:** 2026-08-16  
**Scope:** local MCP process/runtime boundary only  
**Supersedes:** the MCP SDK/package/runtime-currentness statements in `threat-model.md` §§0, 2.2, and 6 when this migration is merged. The rest of the accepted threat model remains in force.

## Why this addendum exists

The original threat model was written while the repository used `@modelcontextprotocol/sdk` v1 and a hand-connected `StdioServerTransport`. The pre-T3 migration changes that protocol boundary without changing the Toast product boundary. Keeping the historical threat model intact preserves why earlier controls exist; this addendum records what is different now instead of pretending the old current-state prose still describes the executable.

## Current MCP runtime boundary

The reviewed target runtime uses the stable MCP TypeScript SDK v2 package split:

- `@modelcontextprotocol/server` is the production server dependency;
- `@modelcontextprotocol/client` is a development/test dependency used for executable protocol verification;
- Node.js `>=20` remains the runtime floor;
- local process stdio is served through the official `serveStdio(factory)` entry from `@modelcontextprotocol/server/stdio`;
- one cheap `createServer()` factory is used for both the legacy 2025 protocol era and the supported 2026-07-28 era;
- remote Streamable HTTP remains out of scope and no network listener is introduced by this migration.

A direct hand-wired `McpServer.connect(new StdioServerTransport())` would remain a legacy-only 2025 boundary even on v2. The migration therefore uses `serveStdio(factory)` deliberately rather than merely changing import paths.

## Protocol state is not application state

The 2026 protocol's stateless request model does **not** authorize making Toast application state global, durable, or cross-tenant. The following ownership remains process/application scoped and must keep its existing isolation rules:

- validated `RuntimeConfig` identity and module-private client credentials;
- OAuth bearer-token cache;
- Standard API rate-limit state;
- restaurant/location registry and future capability context;
- future configuration/menu caches;
- future report retrieval/normalization state.

The MCP serving entry owns protocol-era and connection state. Toast application dependencies remain explicit process-owned objects captured by the server factory. A later tool handler must consume those same objects rather than constructing a second credential, token, transport, retry, or location stack.

## Fail-closed stdio startup and runtime errors

`serveStdio()` owns and starts its wire transport asynchronously. Its out-of-band `onerror` callback is therefore a separate failure path from the top-level `main().catch(...)` path used for configuration/startup exceptions.

The repository wraps that entry in `startStdioServer()` so an out-of-band transport error:

1. is rendered only as the static message `toast-pos-mcp stdio transport error`;
2. never interpolates or attaches the SDK/transport `Error` object;
3. sets a non-zero process exit status;
4. closes the owned stdio handle deterministically;
5. is idempotent if the SDK reports more than one error while teardown is underway.

This matters operationally: supervisors and scripts must not observe a broken MCP transport followed by process exit status `0`.

## Stdout/stderr boundary

Stdout remains reserved exclusively for MCP framing. Human-readable diagnostics use stderr and remain static/sanitized. No bearer token, client credential, upstream body, caught error message, stack, or `cause` is emitted by the repository's process boundary.

## Executable compatibility proof required before merge

Static source review does not establish protocol compatibility. The migration is not CLEAN until a clean authentic install at the exact reviewed head proves:

- a legacy 2025 client connects to built `dist/index.js` and observes no Toast tools;
- a client pinned to protocol revision `2026-07-28` connects to the same executable, with no legacy fallback available;
- closing and reconnecting spawns a new process and does not rely on hidden MCP-session state surviving restart;
- configuration/consent failures still exit non-zero before serving stdio;
- forced stdio transport failure exits non-zero and emits only the static diagnostic;
- stdout contains only MCP framing;
- no Toast reporting tool, resource, prompt, network listener, or write operation appears in this migration.

The lockfile must be generated by npm from the authentic v2 packages and inspected before these gates count. Validation doubles or a v1 lockfile do not qualify.

## Supply-chain delta

The historical threat model describes the v1 package graph and its then-current advisories. Once this migration is accepted, those statements become historical evidence rather than the active dependency inventory. The release/merge record must capture the npm-generated v2 lockfile, package dry-run contents, and any current audit/advisory state actually observed at that exact dependency graph.

## Unchanged boundaries

This migration does not change:

- the structurally read-only Toast policy;
- Merchant-consent and third-party-processing obligations;
- guest-linked-data exclusions;
- restaurant/location isolation requirements;
- Standard-versus-Analytics source separation;
- deterministic report requirements;
- prohibition on remote transport without a separate reviewed threat model;
- prohibition on GitHub Actions as a substitute for required local validation evidence.
