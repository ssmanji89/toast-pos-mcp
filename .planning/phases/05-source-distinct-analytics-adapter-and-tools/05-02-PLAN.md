<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Exact source head → supported runtime checks | The implementation and lockfile must remain identical across authentic Node 20 and Node 22 validation. |
| Mutation harness → safety claims | Every written guard requires a failing focused proof, not an aggregate pass alone. |
| Builder → independent reviewer | Review evidence must originate from a reviewer who did not approve their own implementation. |
| Local synthetic evidence → public claim | Synthetic results can prove local behavior but cannot grant live service, consent, or release evidence. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T5-001-E-01 | Tampering | implementation candidate | mitigate | Capture matching before-and-after immutable SHA values around every Node/package command and repeat them after any head change. |
| T5-001-E-02 | Repudiation | PR evidence | mitigate | Record commands, exits, discovered files, test total, package contents, mutation outcomes, DOX, reviewer, and exact reviewed SHA. |
| T5-001-E-03 | Tampering | guard evidence | mitigate | Require a named focused mutation failure for every matrix guard; a survivor blocks review completion. |
| T5-001-E-04 | Elevation of privilege | product or release claim | mitigate | State D-08 and D-09 boundaries and external live/consent/release gates in docs and PR evidence. |
| T5-001-E-SC | Tampering | npm dependency supply chain | mitigate | Use authentic `npm ci --no-audit --no-fund` and `npm pack --dry-run --json` with each required Node runtime. |
</threat_model>
